# Legal Document RAG System

A Retrieval-Augmented Generation (RAG) system for asking natural-language
questions about a corpus of legal PDF documents. Answers are generated by
Google Gemini from **only** the document text retrieved for that question, and
every answer is returned with the exact sources — document, page and chunk — it
was grounded on.

The system provides document-based information, **not professional legal
advice**.

---

## Project Overview

Legal documents are long, repetitive and full of cross-references, which makes
them slow to search by hand and a poor fit for a plain keyword search. This
project indexes the documents once, then answers questions against that index:

- **Retrieval** finds the passages that are semantically closest to the
  question, even when the wording differs ("how do I end the contract?" finds
  a clause titled "Termination for Convenience").
- **Generation** asks Gemini to answer using those passages and nothing else,
  under a system instruction that forbids inventing legal facts and requires
  the model to say when the documents do not contain the answer.
- **Citations** make every claim checkable: the answer cites the source inline
  and the API returns the retrieved chunks alongside it.

What the system will not do: give advice, present itself as a lawyer, or fill
gaps with general knowledge without labelling it as such.

## Architecture

```
data/raw/*.pdf
      |
      v
[ ingestion.py ]     LangChain PyPDFLoader -> one Document per page,
      |              keeping source filename and page number
      v
[ chunking.py ]      RecursiveCharacterTextSplitter -> ~512-token chunks
      |              with ~75-token overlap, split on legal boundaries
      v
[ embeddings.py ]    sentence-transformers/all-MiniLM-L6-v2 -> 384-dim
      |              normalised vectors, encoded in batches of 32
      v
[ vector_store.py ]  one FAISS IndexFlatIP per document, saved with its
      |              own chunks.json to vectorstore/<document_id>/
      v
[ retrieval.py ]     embed question -> search that document's own index
      |              -> top-k chunks
      v
[ rag.py ]           grounded prompt + system instruction -> Gemini
      |
      v
   answer + sources  (served by main.py to the browser and to /ask)
```

Ingestion through vector-store creation happens **once**, offline, when you
build the index. At question time only the short query is embedded and
searched, so answering is fast.

| File | Responsibility |
| --- | --- |
| `src/ingestion.py` | Load PDFs, compute corpus statistics |
| `src/chunking.py` | Split pages into overlapping chunks, chunk statistics |
| `src/embeddings.py` | Load the embedding model (cached), encode text in batches |
| `src/vector_store.py` | Create, save and load one FAISS store per document |
| `src/retrieval.py` | Embed a question and search a document's own index |
| `src/rag.py` | Build the grounded prompt and call Gemini |
| `src/evaluation.py` | ROUGE-L, faithfulness and answer relevance |
| `main.py` | FastAPI app: `/`, `/health`, `/documents`, `/upload`, `/ask`, `/evaluate` |

## Installation

Requires Python 3.10 or newer.

```bash
cd legal-rag
python -m venv venv
```

Activate the virtual environment:

```bash
venv\Scripts\activate       # Windows
source venv/bin/activate    # macOS / Linux
```

Install the dependencies:

```bash
pip install -r requirements.txt
```

The first run downloads the `all-MiniLM-L6-v2` embedding model (about 90 MB)
from Hugging Face, so the first build needs an internet connection. It is
cached locally afterwards.

## Environment Setup

The Gemini API key is read from a `.env` file in the project root and is never
hard-coded or logged.

```bash
cp .env.example .env        # Windows: copy .env.example .env
```

Then edit `.env`:

```
GEMINI_API_KEY=your_actual_key_here
```

Get a free key from [Google AI Studio](https://aistudio.google.com/apikey).

Optionally pin a different model:

```
GEMINI_MODEL=gemini-2.5-flash
```

`.env` is listed in `.gitignore` — do not commit it.

## Adding Documents

Put your PDF files in:

```
data/raw/
```

Any number of PDFs is fine. Files at the top level of `data/raw/` are read in
filename order (subfolders are not searched), and each page becomes a separate
LangChain `Document` that remembers which file and page it came from. Scanned image-only PDFs will not work: the text has to be
extractable, so run OCR first if needed.

Inspect what was loaded at any time:

```bash
python -m src.ingestion              # corpus statistics
python -m src.ingestion --tokenizer  # exact token counts (slower)
python -m src.chunking               # chunk statistics and sample chunks
```

## Building the Vector Stores

Every document gets **its own** vector store. Nothing is merged into a shared
index, so adding one contract never re-embeds the others.

```bash
python -m src.vector_store
```

This gives each PDF in `data/raw/` its own folder:

```
vectorstore/
├── registry.json                    which documents are indexed
├── service_agreement/
│   ├── index.faiss                  that document's vectors
│   └── chunks.json                  its chunks: page, chunk index and text
└── vendor_nda/
    ├── index.faiss
    └── chunks.json
```

The folder name (`service_agreement`) is the **document id**, derived from the
PDF filename. `chunk_index` is the position inside that document's own index,
so `chunks.json[i]` is always the chunk behind FAISS result `i`.

Documents that already have a store are skipped, so the command only does work
for new files. Other useful flags:

```bash
python -m src.vector_store --list                 # show what is indexed
python -m src.vector_store --pdf data/raw/nda.pdf # index one file only
python -m src.vector_store --rebuild              # rebuild every store
```

Test retrieval on its own, without involving Gemini. `-d` picks the document to
search; leave it out to search every store and merge the hits by similarity:

```bash
python -m src.retrieval "What are the termination conditions?" -d service_agreement
```

And the full pipeline from the command line:

```bash
python -m src.rag "What are the termination conditions?" -d service_agreement
```

## Running the API

```bash
uvicorn main:app --reload
```

At startup any PDF in `data/raw/` without a store gets one. Each store is
loaded on first use and cached until its files change. If nothing is indexed
the server still starts, and `/health` and the web page will tell you to
upload a PDF.

## Accessing the Application

| What | URL |
| --- | --- |
| Frontend | http://127.0.0.1:8001/ui |
| Swagger UI | http://127.0.0.1:8001/docs |
| ReDoc | http://127.0.0.1:8001/redoc |
| OpenAPI schema | http://127.0.0.1:8001/openapi.json |
| Health check | http://127.0.0.1:8001/health |

### Endpoints

**`GET /health`**

```json
{
  "status": "running",
  "documents_indexed": 3,
  "vectors": 412
}
```

**`GET /documents`**

Every document that has its own store:

```json
{
  "count": 2,
  "documents": [
    {
      "document_id": "service_agreement",
      "source_file": "service_agreement.pdf",
      "page_count": 14,
      "chunk_count": 212,
      "embedding_dimension": 384,
      "created_at": "2026-09-02T11:22:00+00:00"
    }
  ]
}
```

**`POST /upload`**

Saves the PDF into `data/raw/` and builds a store for **that file only**. Every
other document keeps its existing index.

**`DELETE /documents/{document}`**

Removes one document's index and chunks file. Because the stores are separate,
nothing else has to be rebuilt.

**`POST /ask`**

`document` is a document id or a PDF filename. Leave it out to search every
store and merge the results by similarity.

Request:

```json
{
  "question": "What are the termination conditions?",
  "top_k": 5,
  "document": "service_agreement"
}
```

Response:

```json
{
  "question": "What are the termination conditions?",
  "document": "service_agreement",
  "answer": "Either party may terminate for convenience upon thirty (30) days prior written notice [service_agreement.pdf, page 4, chunk 12].",
  "sources": [
    {
      "document_id": "service_agreement",
      "source_file": "service_agreement.pdf",
      "page": 4,
      "chunk": 12,
      "similarity": 0.7421
    }
  ]
}
```

Error responses carry a `detail` message:

| Status | Meaning |
| --- | --- |
| 422 | The question failed validation (empty, or shorter than 3 characters) |
| 500 | `GEMINI_API_KEY` is missing or invalid |
| 502 | The Gemini API call failed |
| 404 | The requested `document` is not indexed |
| 409 | No documents have been indexed yet |

You can try `/ask` directly from the Swagger page at `/docs`.

## Evaluation

The evaluation suite lives in `src/evaluation.py` and reads its questions from
`evaluation/questions.json`:

```json
[
  { "question": "What are the termination conditions?", "reference_answer": "..." }
]
```

Three metrics are reported per question:

| Metric | Needs a reference answer? | How it is computed |
| --- | --- | --- |
| **ROUGE-L** | Yes | `rouge-score`, longest-common-subsequence F-measure. Deterministic, no LLM. |
| **Faithfulness** | No | Is every claim in the answer supported by the retrieved context? |
| **Answer Relevance** | No | Does the answer address the question that was asked? |

Faithfulness and answer relevance are LLM-judged, with two interchangeable
backends:

- **RAGAS** (default) — the library's `Faithfulness` and `AnswerRelevancy`
  metrics, driven by Gemini (`provider="google"`) with the same local
  all-MiniLM-L6-v2 embeddings the retriever uses. No OpenAI key is involved.
- **Built-in Gemini judge** (fallback) — a single scoring call through
  `google-genai`. Used automatically whenever the RAGAS backend cannot be
  constructed or fails, so a RAGAS version change never breaks an evaluation
  run. Its scores come from one judgement rather than RAGAS's multi-step
  decomposition, so treat them as indicative.

Run it:

```bash
python -m src.evaluation                     # RAGAS, falling back to the judge
python -m src.evaluation --metrics judge     # force the built-in judge
python -m src.evaluation --metrics none      # ROUGE-L only, no LLM judging
python -m src.evaluation --limit 3 --detailed
```

Results are printed as a table and saved to `evaluation/results/` as JSON (full
text) and CSV (spreadsheet-friendly):

```
#  QUESTION                                    ROUGE-L  FAITHFUL  RELEVANCE
1  What are the termination conditions?          0.667     0.920      0.880
2  What are the payment terms?                   0.541     0.950      0.910
   AVERAGE                                       0.604     0.935      0.895
```

### Writing reference answers

`evaluation/questions.json` ships with 12 questions and **empty**
`reference_answer` fields, because a reference answer has to be taken from your
actual documents — inventing one would measure nothing.

Fill each `reference_answer` in with the correct answer read out of your own
PDFs. Until you do, those rows show `n/a` for ROUGE-L; faithfulness and answer
relevance are reference-free and are still scored.

## Limitations

**Retrieval errors.** Retrieval is dense-vector only, with no keyword or hybrid
search. A question whose wording is semantically distant from the clause that
answers it can miss, and a defined term used in an unusual sense can pull the
wrong clause. Nothing that is not retrieved can appear in the answer, so a
retrieval miss is silent.

**Chunking limitations.** Chunks are cut by character count, not by legal
structure, so a clause that spans a page break or runs longer than one chunk
can be split across two. Chunks carry no awareness of the section they belong
to, so a sub-clause can be retrieved without the heading that qualifies it, and
cross-references ("as defined in Section 4") are not resolved.

**Embedding limitations.** `all-MiniLM-L6-v2` is a small general-purpose model
with a **256-token maximum sequence length**. The default chunk size is 512
tokens, so text past the halfway point of a long chunk does not influence its
vector — Gemini still reads the whole chunk, but retrieval effectively matches
on the first half. Run `python -m src.chunking` to see how many chunks exceed
the window, and use `--chunk-size 256` if you prefer full coverage over context
length. The model is also not trained on legal language, so it can miss
distinctions that matter in a contract.

**Hallucination risk.** The system instruction forbids inventing facts and
requires an explicit "not enough information" response, and the temperature is
low, but no prompt eliminates hallucination. The model can still merge clauses
from two different contracts, over-generalise, or attach a correct statement to
the wrong citation. Always check the answer against the cited page.

**Legal-domain complexity.** The system reports what the retrieved text says.
It does not interpret it, does not know which clauses have been superseded by
amendments or side letters, does not account for governing law or jurisdiction,
and cannot tell you whether a clause is enforceable.

**Dataset limitations.** Answers can only be as good and as current as the PDFs
in `data/raw/`. Scanned documents without an OCR text layer yield nothing, and
complex tables and multi-column layouts often extract in a jumbled order.

**API dependency.** Generation requires a live Gemini API key and internet
access. Rate limits, quota exhaustion and model deprecations will surface as
502 errors. Document text for the retrieved chunks is sent to Google's API at
question time — consider that before pointing this at confidential material.

**No replacement for professional legal advice.** This is a document search and
summarisation tool. It is not a lawyer, does not create a solicitor-client or
attorney-client relationship, and its output must not be relied on for any
legal decision. Consult a qualified lawyer.

## Project Structure

```
legal-rag/
├── data/raw/               your PDF documents go here
├── vectorstore/            one FAISS index + chunks.json per document
├── src/
│   ├── __init__.py         shared path constants
│   ├── ingestion.py        Task 1 - PDF loading and corpus statistics
│   ├── chunking.py         Task 2 - text splitting and chunk statistics
│   ├── embeddings.py       Task 3 - sentence-transformers embeddings
│   ├── vector_store.py     Task 4 - per-document FAISS create / save / load
│   ├── retrieval.py        Task 5 - top-k search inside a document's store
│   ├── rag.py              Task 6 - grounded Gemini generation
│   └── evaluation.py       ROUGE-L, faithfulness, answer relevance
├── frontend/
│   ├── templates/index.html
│   └── static/{style.css, script.js}
├── evaluation/questions.json
├── main.py                 FastAPI application
├── requirements.txt
├── .env.example
└── README.md
```

Every module in `src/` runs standalone for testing, for example
`python -m src.chunking`. All commands are meant to be run from the project
root.
